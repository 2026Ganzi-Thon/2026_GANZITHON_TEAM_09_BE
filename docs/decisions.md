# 행운핑 설계 결정 기록

- 2026년 11월 16일 작성 · @고은우
- 요구사항: [prd.md](prd.md) · 구조: [architecture.md](architecture.md) · 보안: [../SECURITY.md](../SECURITY.md)
- 결정마다 **왜 그렇게 했는지, 무엇을 버렸는지, 한계는 무엇인지**를 적는다. 결정을 바꾸면 줄을 지우지 말고 「바뀜」을 붙인다.

## D-01. 로그인 없이 익명 계정으로 시작한다

- **결정:** 닉네임만 받아 익명 계정을 만들고, 세션 토큰을 HttpOnly 쿠키 `__Host-hp_session`에 담는다(로컬은 `hp_session`, D-11). 서버는 토큰의 SHA-256 해시만 저장한다(ACC-01).
- **이유:** 우울·무기력한 사용자는 가입 단계에서 이탈한다. 이름·이메일·전화번호를 받지 않으면 유출될 개인정보 자체가 줄어든다.
- **버린 것:** 카카오 로그인(이탈 증가, 개인정보 수집), 이메일 가입(비밀번호 관리 부담).
- **한계:** 브라우저 데이터를 지우면 계정이 사라진다. 차단당한 사람이 새 계정으로 다시 들어올 수 있다(prd 남은 위험).

## D-02. 쿠키 + CSRF 토큰 방식으로 인증한다

- **결정:** 화면과 API를 같은 도메인으로 두고, `SameSite=Lax` 쿠키 + `XSRF-TOKEN` 이중 제출로 막는다(SEC-04).
- **이유:** 토큰을 자바스크립트가 읽을 수 없어 XSS가 생겨도 세션이 바로 털리지 않는다. 같은 도메인이라 CORS 설정이 필요 없다.
- **버린 것:** JWT를 `localStorage`에 저장(XSS 한 번에 토큰 유출, 만료 전 폐기 어려움).
- **한계:** 프론트와 API가 다른 도메인이 되면 SameSite·CSRF 설정을 다시 봐야 한다.

## D-03. 모듈형 모놀리스로 만든다

- **결정:** Spring Boot 앱 하나, 기능별 패키지(account·group·mood·mission·…)로 나누고 ArchUnit으로 경계를 지킨다. 다른 모듈은 `XxxQuery` 인터페이스와 이벤트로만 만난다.
- **이유:** 3명이 테이블 소유 기준으로 나눠 동시에 개발하면서도, 배포·트랜잭션·로컬 실행은 하나로 단순하게 유지한다.
- **버린 것:** 마이크로서비스(해커톤 규모에 운영 비용 과다), 경계 없는 단일 패키지(3명이 같은 파일을 고쳐 충돌).
- **한계:** 모듈이 같은 DB를 쓰므로 경계는 코드 규칙으로만 지켜진다. 규칙 위반은 ArchUnit 테스트가 잡는다.

## D-04. 캐릭터 성장은 서버만, 정수로 저장해 계산한다

- **결정:** 날짜별 구성원 수·완료 수를 정수로 저장하고 성장은 그 합으로 계산한다(CHR-04). 클라이언트가 보낸 수치는 받지 않는다(SEC-09).
- **이유:** 소수를 누적 저장하면 오차가 쌓이고, 클라이언트 값을 믿으면 조작할 수 있다. 정수 원본이 있으면 언제든 다시 계산하고 검증할 수 있다.
- **버린 것:** 캐릭터 행에 진행도 컬럼을 두고 더해 가기.
- **한계:** 조회할 때마다 합을 구한다. 캐릭터 하나에 수십 행이라 문제가 되지 않는다.

## D-05. 도움받기 필터는 기기에서 한다

- **결정:** 생년월일·지역·하는 일은 기기(IndexedDB)에만 저장하고, 서버는 전체 목록과 규칙만 내려준다. 기기가 걸러서 보여준다(HELP-03).
- **이유:** 정신건강 앱에서 "누가 어떤 지원 대상인지"를 서버에 모으지 않는다. 오프라인에서도 도움받기 탭이 열린다.
- **버린 것:** 서버에서 맞춤 목록 계산(민감정보 수집, 오프라인 불가).
- **한계:** 기기를 바꾸면 선택 정보를 다시 넣어야 한다.

## D-06. 외부 AI(LLM)를 쓰지 않는다

- **결정:** 미션 배정·문구·도움 연결·점검 결과 문장을 모두 규칙 기반 코드와 시드 데이터로 만든다(MIS-09).
- **이유:**
  1. 같은 입력이면 같은 결과가 나와 왜 그 미션·그 기관이 보였는지 설명할 수 있다.
  2. 기분·점검 같은 건강 정보를 외부 AI 서비스로 보내지 않는다.
  3. 출력 검증, 프롬프트 인젝션, API 키 관리, 호출 비용, 응답 지연이 모두 사라진다.
  4. 미션 20쌍은 이미 밖/안 문구가 있어 AI가 더하는 가치가 작았다.
- **버린 것:** 미션 문구를 LLM으로 다듬기(초기 기획에 있었음).
- **한계:** 문구가 매일 같다. 주제 20쌍과 3일 중복 제외(MIS-02)로 반복감을 줄인다.

## D-07. 서버 1대, 예약 작업은 `job_runs`로 한 번만 실행한다

- **결정:** `@Scheduled` + 처리 기록 테이블로 같은 날짜를 두 번 처리하지 않는다. 확정 처리는 멱등이다(NFR-03·04).
- **이유:** 시연 규모에서 분산 잠금·메시지 큐는 과하다. 서버가 꺼졌다 켜져도 밀린 날짜를 따라잡는다(CHR-03).
- **버린 것:** Quartz 클러스터, 외부 큐.
- **한계:** 서버를 2대 이상으로 늘리면 ShedLock으로 바꿔야 한다(architecture 4.1).

## D-08. 날짜는 주입한 `Clock`으로만 계산한다

- **결정:** `LocalDate.now()` 직접 호출을 금지하고(ArchUnit), 모든 날짜 계산은 KST `Clock`을 주입받는다(DEMO-02).
- **이유:** 자정 확정, 일요일 점검, 3일 연속 같은 날짜 규칙을 테스트에서 시각을 고정해 검증할 수 있다.
- **한계:** 앱 시계는 하나라 사용자마다 다른 날짜를 줄 수 없다. 그래서 시연의 날짜 이동은 서버가 아니라 프론트 목업에서 한다(D-12).

## D-09. 주간 점검은 공개 선별 도구를 쓰되, 점수는 보여주지 않는다

- **결정:** PHQ-2·GAD-2 문항으로 묻고, 응답에는 점수 없이 결과 문장과 연결할 곳만 준다(CHK).
- **이유:** 검증된 선별 문항이라 근거를 댈 수 있다. 점수를 보여주면 앱이 진단하는 것처럼 읽힌다.
- **한계:** 선별이지 진단이 아니다. 화면마다 "진단이 아니에요"를 표시하고, 위기 감지는 하지 않는다고 고지한다.

## D-10. Spring Boot 4.1을 쓴다

- **결정:** Spring Boot 4.1.2(Spring Security 7, Jackson 3, Hibernate 7), Java 21, Gradle 9. 버전은 `gradle/libs.versions.toml` 한 곳에서 정한다.
- **이유:** 3.5는 무료 보안 패치가 2026년 6월에 끝났고, 4.0도 2026년 12월 31일에 끝난다. 4.1은 2027년 7월까지 패치를 받는다. 공개 레포에서 지원 끝난 프레임워크를 쓰면 의존성 검증(SEC-14)과 맞지 않는다. Security 7의 `csrf.spa()`로 SPA용 CSRF 설정을 공식 API로 쓸 수 있다.
- **버린 것:** Spring Boot 3.5(자료가 많지만 지원 종료), 4.0(지원 6주 남음).
- **한계:** 3.x 예제와 패키지 이름이 다른 곳이 있다(Jackson `tools.jackson`, 테스트 슬라이스 패키지, 웹 스타터 이름 `webmvc`). AI가 3.x 기준 코드를 내놓기 쉬우니 공식 문서와 대조한다(ai-usage.md 1절 3번).

## D-11. 기기 이전은 MVP에서 만들지 않고, 세션 쿠키 하나를 단단히 지킨다

- **결정:** 다른 브라우저·기기에서 기존 계정에 들어가는 기능(기기 이전 코드)은 MVP에서 만들지 않는다. 계정은 처음 만든 브라우저(아이폰은 홈 화면 앱)에 묶인다. 대신 유일한 열쇠인 세션 쿠키를 다음처럼 지킨다.
  - 토큰은 `SecureRandom` 256비트(32바이트)를 Base64URL로 만든다. DB에는 SHA-256 해시만 저장한다.
  - 쿠키 이름은 `__Host-hp_session`이다. 브라우저가 `Secure`·경로 `/`·도메인 없음을 강제해, 하위 도메인이 가짜 세션 쿠키를 심지 못한다. 로컬(http)에서는 이 접두사를 쓸 수 없어 `hp_session`을 쓴다(`haengunping.session-cookie-name`).
  - `HttpOnly`·`Secure`·`SameSite=Lax`, 만료 400일. 로그인이 없어 만료가 곧 계정 상실이므로 줄이지 않는다.
  - 화면(HTML)에도 CSP·HSTS를 붙인다. API는 Spring이, 화면은 프록시(Caddy)가 붙인다. Spring은 프록시 뒤에서 HTTPS 여부를 모르므로 HSTS는 Caddy가 맡는다.
- **이유:**
  1. 이전 코드는 그 자체가 새 열쇠다. 코드를 아는 사람은 기분·점검 결과를 본다. 가장 현실적인 공격은 기술이 아니라 친구 사이의 "코드 좀 알려줘"다.
  2. 안전하게 만들려면 1회용·10분 코드, 시도 횟수 제한, 연결 기기 목록과 폐기까지 필요해 인증 영역이 커진다. 시연 흐름에는 필요 없다.
  3. 탈취돼도 피해는 그 계정 하나다. 이메일·비밀번호가 없어 다른 서비스로 번지지 않고, 도움받기용 나이·지역·직업은 서버에 없다(D-05).
- **버린 것:**
  - 닉네임+PIN 로그인: PIN은 짧아 맞히기 쉽고, 결국 비밀번호 관리 문제가 생긴다.
  - 이메일 복구: 개인정보 수집, D-01과 충돌.
  - 아이디·비밀번호 가입(2026-11-17 검토): 다른 기기 로그인과 비밀번호 변경으로 세션 끊기가 되지만, 가입 단계 이탈이 늘고, 비밀번호 맞히기·다른 사이트에서 털린 비밀번호 재사용 공격이 새로 생긴다. 이메일·전화번호 없이는 비밀번호를 잊으면 복구할 수 없어 계정 상실 문제가 그대로 남는다. 프론트 온보딩도 다시 만들어야 한다.
  - 익명으로 시작하고 마이 탭에서 아이디·비밀번호를 선택 등록(같은 날 검토): 가입 장벽은 그대로지만 API 4개·화면 2개와 비밀번호 보안이 추가된다. 시연 흐름에 필요 없어 서비스화 후보로 둔다.
- **한계:**
  - 브라우저 데이터를 지우거나 기기를 바꾸면 계정을 잃는다.
  - 탈취된 쿠키를 "다시 로그인"으로 끊을 수 없다. 쿠키를 지우면 내 계정도 사라진다.
- **서비스화 때 할 일:**
  1. 기기 이전 코드: 기존 기기에서만 발급, 영문·숫자 12자, 10분 유효, 1회용, 해시 저장, 입력은 IP당 시간당 10회. 새 기기가 연결되면 기존 기기에 알리고, 연결 기기 목록과 "다른 기기 모두 끊기"를 둔다. 기기에만 있는 도움받기 정보는 옮기지 않는다.
  2. 토큰 교체와 재사용 감지: 일정 기간마다 새 토큰을 주고 옛 토큰을 폐기한다. 폐기된 토큰이 다시 오면 그 요청은 거절하고, 사용자에게 탈취 가능성을 알려 연결 기기 목록에서 모르는 기기를 끊게 한다. 세션을 모두 끊으면 로그인이 없어 본인도 계정을 잃으므로 자동으로 모두 끊지는 않는다.

## D-12. 시연의 날짜 이동은 프론트 목업에서 하고, 실서버는 출시 그대로 둔다

- **결정(2026-11-18):** 실서버에는 서버 시계를 바꾸는 API(`PUT /demo/clock`)를 만들지 않는다. 시연은 둘로 나눈다.
  - 처음 열기 → 닉네임 → 동의 → 기분 → 미션 → 다 했어요 → 그룹·도움받기: **실서버**에서 새 계정으로 라이브. 심사위원도 같은 주소로 직접 체험한다.
  - 일요일 주간 점검, 3일 연속 도움 카드, 캐릭터 단계 상승·완성처럼 며칠이 걸리는 장면: **프론트 목업**(`VITE_API_MODE=mock`, 데이터·시계가 그 기기 안에만 있음)에서. 목업은 같은 서버의 하위 도메인(`DEMO_SITE_ADDRESS`)에 정적 사이트로 올린다.
  - 실서버는 행사 직전 출시 직후 상태로 비우고, 온라인 그룹 자리만 시드로 넣는다(DEMO-03). 행사장 공유 IP 때문에 계정 생성 한도는 행사 설정으로 조정한다(DEMO-05).
- **이유:**
  1. 앱 시계는 하나다(D-08). 서버 시계를 옮기면 그 순간 심사위원이 만든 계정의 날짜도 같이 옮겨진다. 처음부터 체험하는 사람과 날짜를 옮기는 발표자가 한 서버를 함께 쓸 수 없다.
  2. 목업에는 시연 시드·시계·대기부터 모드·시연용 초대 코드가 이미 있다. 서버에 같은 것을 만들면 시연 전용 API와 그 권한 검사(SEC-13)가 늘어난다. 실서버에 시계 API가 없으면 그 공격 표면(T12)도 없다.
  3. 행사장 네트워크가 불안해도 목업 장면은 끊기지 않는다.
- **버린 것:**
  - 실서버 하나에서 `demo` 프로필 시계 사용: 1번 이유로 처음부터 체험과 함께 쓸 수 없다. 발표 시간과 체험 시간을 나눠야 한다.
  - 시연 전용 서버를 하나 더(같은 VM, `demo` 프로필): 분리는 되지만 api·DB가 하나 더 늘고 시계 API·시드·권한 검사를 서버에 만들어야 한다.
  - 사용자별 시계: 모든 날짜 계산이 사용자 문맥을 알아야 해 변경이 크다.
  - 목업만으로 시연: 심사 기준의 "핵심 기능이 실제 시연에서 동작"을 보여 줄 수 없고, 목업과 실서버의 동작 차이가 드러나지 않는다.
- **한계:** 목업 장면은 실서버 코드가 아니다. 발표에서 "며칠이 걸리는 장면은 기기 안 시뮬레이션"이라고 말한다. 목업과 실서버가 다르게 동작하지 않도록 계약(api.md)이 바뀌면 목업도 맞춘다.

## D-13. 주간 점검은 답을 저장하지 않고, 결과 코드만 남긴다

- **결정(2026-11-18):** `checks`에는 `answers`를 두지 않는다. 남기는 것은 주(`week_start`), 상태(`DONE`·`DISMISSED`), 결과 코드(`result_codes`), 시각이다. 판정은 `check.domain.CheckRules`의 순수 함수로 하고, 점수는 응답·로그·DB 어디에도 담지 않는다(CHK-04).
- **이유:**
  1. 저장된 답을 다시 읽는 요구사항이 없다. 응답은 결과 코드·문장·구역만 주고(CHK-04), 도움받기 순서 신호도 결과만 쓴다(HELP-06 `checkAboveThreshold`).
  2. 우울·불안 문항 답은 가장 민감한 정보다. 쓰지 않는 것은 모으지 않는다(SEC 민감정보 최소 수집). 유출·실수 로그의 피해 범위도 같이 줄어든다.
  3. 결과를 다시 계산해야 할 일이 생겨도(기준 변경) 과거 기록은 그때의 결과로 남는 것이 맞다. 점검은 진단이 아니라 그 주의 참고다.
- **함께 정한 것:**
  - 시각은 요청마다 한 번만 읽어(`ZonedDateTime.now(clock)`) 주차·창을 같이 계산한다. 일요일 23:59:59에 들어온 요청이 중간에 월요일로 넘어가도 주가 갈리지 않는다.
  - 제출·닫기는 `INSERT … ON CONFLICT (user_id, week_start) DO NOTHING`의 영향 행 수로 판정한다. 더블 클릭·동시 요청에도 한 건만 들어가고, 예외를 잡지 않으므로 트랜잭션이 깨지지 않는다.
  - 검사 순서는 동의(403) → 답 형식(400) → 점검 기간·중복(409)이다(프론트 목업과 같다). `@Valid`는 동의보다 앞서 400을 내므로 형식은 컨트롤러에서 직접 검사하고, `common.error.FieldValidationException`으로 `fields`를 싣는다.
  - 닫기(`dismiss`)는 동의·창과 무관하게 204이고 멱등이다. 이미 기록이 있으면 그대로 둔다(목업과 같음).
  - 낮은 기분 일수는 우울·불안이 모두 기준 미만일 때만 `MoodQuery`로 묻는다.
  - 다른 모듈에는 `check.CheckQuery`로만 연다: `aboveThresholdSince`(HELP-06), `usersWithRecord`(NOTI-03). 점수·결과 코드 자체는 내주지 않는다.
- **버린 것:**
  - 답을 암호화해 저장: 쓰지 않는 데이터를 지키는 비용만 늘어난다.
  - 답을 저장해 두고 기준이 바뀌면 다시 계산: 요구사항에 없고(1번), 점검 결과는 그 주의 참고라 소급할 이유가 없다.
  - `@Valid`로 형식 검사: 동의 없는 사용자에게 400이 먼저 나가 목업과 어긋난다.
- **한계:** 같은 주에 한 번 닫으면 다시 점검할 수 없다(CHK-05). 잘못 눌러 닫은 경우의 복구는 만들지 않았다. 점검 결과가 기준 이상이어도 앱은 위기를 감지하지 못한다(prd 남은 위험).
